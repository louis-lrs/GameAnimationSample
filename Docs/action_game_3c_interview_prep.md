# 动作游戏 3C 岗位面试准备稿

> 适用对象：准备 UE 动作游戏 / 3C / 动画系统 / 联机战斗客户端岗位的候选人。  

## 1. 先明确岗位本质

3C 岗位不是“写移动逻辑”或“接动画资源”。本质是把 **输入、相机、角色胶囊体、动画表现、战斗判定、网络同步、性能预算** 放进同一个系统里，让玩家感觉角色可控、可信、好看，并且在复杂场景下仍然可维护。

面试官通常在判断四件事：

1. 你能否从控制权出发拆问题：什么时候输入优先，什么时候动画接管，什么时候服务器权威。
2. 你能否讲清动画系统和移动系统的边界：胶囊体、Root Motion、Aim Offset、Motion Warping、Montage、Pose Search 怎么协作。
3. 你能否处理联机动作游戏的误差：预测、插值、外插、校正、延迟补偿、反作弊怎么取舍。
4. 你能否把性能优化讲成可验证方案：瓶颈在哪里，改了什么，收益量级，代价和边界是什么。

## 2. 经历表达口径

面试时可以这样概括经历，避免暴露原始项目信息：

> 我参与过 UE 动作类项目中的 3C、动画系统、联机移动同步和性能优化工作。项目里涉及基础移动、复杂姿态切换、载具/滑翔/攀爬类特殊移动、多人同屏角色动画预算、弱网下移动校验，以及动画蓝图和骨骼评估性能优化。我的优势是能把玩家手感、动画表现、网络权威和性能预算放在一起做取舍，而不是只看单点功能。

数字类信息统一用“量级”表达：

- 精确硬件配置：改成“低端机 / 主流低配环境”。
- 精确同屏人数：改成“十余名角色 / 多人同屏”。
- 精确耗时：改成“毫秒内 / 几十微秒级 / 二到三成量级收益”。
- 精确弱网参数：改成“百毫秒级延迟 + 少量丢包”。
- 精确发包频率：改成“几十包每秒量级，并配合合包、限流和状态压缩”。
- 精确服务器帧率：改成“低帧率 DS 压力场景，需要控制峰值和可降级策略”。

## 3. 高频问题与回答技术要点

### Q1：你怎么理解 3C 岗位？

**考点**：是否知道 3C 的本质不是动画、移动、镜头任何单点，而是控制体验系统。

**回答要点**：

- Character：角色输入响应、移动模式、姿态、碰撞、动画状态。
- Camera：视角表达、准星/锁定/相机碰撞、FPP/TPP 一致性。
- Control：输入缓冲、取消窗口、Root Motion 与输入驱动的权衡。
- 3C 的核心矛盾是“玩家控制感”和“动画表现正确性”之间的平衡。

**可用回答**：

> 我理解 3C 的核心是控制体验。角色不是单纯被动画驱动，也不是只按物理胶囊体移动，而是要在输入、胶囊体、动画、镜头和战斗规则之间建立稳定关系。高频移动和战斗操作一般输入优先，动画通过 Warping、AO、Pose Blend 去贴合；强交互动作如攀爬、上车、处决，可以让动画接管更多位移，但要保证可预测、可打断和可同步。

### Q2：Root Motion 和 Input Driven 怎么取舍？

**考点**：是否能说清控制权归属。

**回答要点**：

- Input Driven：适合高频移动、转向、战斗走位，手感强，可预测性好。
- Root Motion：适合强表现、强约束动作，如处决、攀爬、跳跃落点、上车、击飞。
- 联机项目要考虑服务器复现和误差校正，不能只从本地表现出发。
- 折中方案：输入驱动胶囊体，动画用 Motion Warping / Distance Matching / Stride Warping 贴合。

**原理补充**：

Root Motion 让动画根骨骼决定位移，表现自然但同步和可控性成本更高；Input Driven 由移动组件或角色逻辑决定胶囊体位移，动画跟随胶囊体，手感和网络预测更稳定。

**可用回答**：

> 我会先看动作是否需要强确定时间轴和强玩家控制。普通移动、射击走位、近战微操优先 Input Driven，避免动画抢控制权。攀爬、处决、上车这类动作可以用 Root Motion 或动画驱动片段，但要把入口、出口、打断、碰撞和服务器校验设计清楚。很多情况下我会让胶囊体仍由逻辑驱动，再用 Motion Warping 和 Pose Warping 修正表现。

### Q3：高速位移下客户端和服务器位置不一致怎么处理？

**考点**：是否区分延迟、采样间隔、平滑性和权威一致性。

**回答要点**：

- 提高发包频率不能降低 RTT，只能降低状态采样间隔。
- 固定轨迹技能：同步初始参数、时间戳、曲线 ID，由客户端和服务器各自复现。
- 自由输入移动：客户端预测，服务器校验，客户端平滑纠正。
- 高风险 PVP 技能：服务器权威更强；偏探索/表现移动：可适当提高客户端信任，但要异常检测。

**原理补充**：

高速移动会放大误差：同样 100ms 延迟，速度越高，位置差越大。解决问题不能只靠更频繁发包，而要减少不可预测自由度，或让双方基于同一参数复现轨迹。

**可用回答**：

> 我会先分类。如果是固定轨迹突进，尽量不要逐帧同步位置，而是同步技能 ID、起点、方向、开始时间和曲线参数，让服务器和客户端基于同一轨迹计算。自由移动则需要客户端预测和服务器校验，纠正时做平滑避免拉扯。发包频率只改善采样连续性，不解决网络延迟本身，真正要处理的是预测、补偿、校正和规则约束。

### Q4：CMC 的网络移动大致流程是什么？

**考点**：是否理解 UE CharacterMovementComponent 的预测和纠正机制。

**回答要点**：

- 主控端产生输入并本地预测移动。
- 客户端把 Move 发送给服务器。
- 服务器复现移动并判断误差。
- 误差可接受则确认，不可接受则下发校正。
- 客户端收到校正后回滚/重放或平滑到服务器状态。

**原理补充**：

UE CMC 默认支持常见人形移动模式和网络复制。它把 `ACharacter` 与 `UCharacterMovementComponent` 深度绑定，适合传统胶囊体角色，但复杂自定义移动会遇到扩展成本。

**可用回答**：

> CMC 的核心是客户端预测加服务器校正。主控端根据输入先本地执行移动，同时把 Move 发给服务器；服务器复现后比较结果，如果误差在阈值内就确认，否则返回校正数据。模拟端主要做插值和平滑。自定义技能位移时我会特别注意 SavedMove 里要保存哪些输入和状态，否则服务器复现不出来，校正会变得频繁。

### Q5：Mover 相比 CMC 的价值和风险是什么？

**考点**：是否了解 UE 新移动框架，但不盲目追新。

**回答要点**：

- Mover 目标是成为新一代角色移动方案，Epic 文档仍标注为实验性。
- 相比 CMC，它更强调模块化、Actor 类型泛化、更多形状支持、统一回滚、客户端校正、受保护状态和网络物理支持。
- 风险是 API 和数据格式可能变化，项目迁移成本、动画系统衔接、工具链和团队熟悉度都要评估。

**可用回答**：

> 我会把 Mover 看成值得验证的新方向，但不会在生产项目里无脑替换 CMC。它的吸引力在于模块化移动模式、更统一的回滚和状态管理，以及对非传统角色形状和网络物理的扩展潜力。但它仍有实验性风险，所以我会先用复杂移动模式做小范围原型，验证预测、动画衔接、调试工具和性能，再决定是否迁移。

### Q6：Motion Matching 适合解决什么，不适合解决什么？

**考点**：是否知道 Motion Matching 是连续动作选择系统，不是万能战斗系统。

**回答要点**：

- 适合基础移动、起停、转向、姿态过渡、走跑切换。
- 不适合完全接管所有战斗技能，因为战斗需要确定时间轴、判定帧、取消窗口和表现节奏。
- 战斗通常用 Montage / Ability 时间轴 / 状态机保证确定性，再用 Motion Warping 等技术衔接。

**原理补充**：

Motion Matching 通过查询角色当前姿态、速度、轨迹等特征，在 Pose Database 中选择代价最低的动画帧。它减少手写状态机和过渡规则，但依赖数据库质量、特征权重和调试工具。

**可用回答**：

> 我会把 Motion Matching 放在高频连续移动上，比如起步、停步、转向和姿态过渡。战斗技能、受击、处决这类动作，我仍倾向用 Montage 或专用 Ability 时间轴，因为它们需要稳定判定帧、取消窗口和打击节奏。两者之间可以用 Motion Warping、Distance Matching、Pose Blend 做衔接。

### Q7：Pose Search / Motion Matching 落地要注意什么？

**考点**：是否能从“我知道概念”进入“我知道怎么调”。

**回答要点**：

- 数据库按语义分组：Locomotion、Start、Stop、Turn、Jump、Combat Stance 等。
- Feature Channel 要围绕动作目标选择：轨迹、速度、朝向、关键骨骼位置/速度。
- 权重要调试：轨迹权重过高可能忽视姿态，姿态权重过高可能牺牲路径响应。
- 防抖：Continuing Pose Cost、最小切换时间、惯性混合、数据库清理。
- 性能：减少无效样本，按状态分库，缓存查询结果，关注查询耗时和调试可解释性。

**可用回答**：

> 我会先按状态和语义拆数据库，而不是把所有动画扔进一个库。Schema 里特征要和玩法目标对应，比如基础移动重视未来轨迹和速度，战斗姿态更重视朝向和上半身约束。调试时看选中的 pose 为什么被选中，是否因为权重导致脚滑或抖动。性能上要控制样本规模，必要时按状态切库。

### Q8：大体型怪物攻击，服务器不完整跑表现骨骼怎么判定？

**考点**：是否能把表现动画和玩法判定解耦。

**回答要点**：

- 服务器不应完整复刻表现级动画骨骼。
- 建立战斗判定代理：关键骨骼挂点、胶囊、OBB、球、扇形、预烘焙攻击体。
- 攻击由数据时间轴驱动，服务器按关键帧或固定步长更新判定体。
- 客户端可播放更复杂动画，但判定受服务器代理状态约束。
- 大怪可按头、躯干、手臂、尾巴等少量部位分段。

**原理补充**：

服务器关心的是“可复现、可校验、可降级”的玩法数据，不是最终渲染表现。表现骨骼越复杂，服务器成本和同步不一致风险越高。

**可用回答**：

> 我会把大怪的表现骨骼和玩法判定拆开。客户端可以播放完整动画，服务器维护简化的战斗代理，比如头、手、尾巴等关键部位的胶囊或 OBB，再用数据时间轴控制攻击体出现、移动和失效。这样服务器不用跑完整表现动画，也能保证命中判定可复现。

### Q9：PVP 技能碰撞和延迟补偿怎么设计？

**考点**：是否能按风险分级，而不是统一套一个方案。

**回答要点**：

- 命中、伤害、控制效果必须服务器权威。
- 主控端可先表现命中反馈，但最终以服务器结算为准。
- 近战可用攻击体时间轴 + 服务器回放关键帧。
- 射击/投射物可按项目需要使用 Lag Compensation 或 Rewind。
- 延迟补偿要有上限，避免高延迟玩家反向伤害公平性。

**可用回答**：

> PVP 里我会把表现反馈和最终结算分开。客户端可以先播命中感和特效，但伤害、控制、资源消耗必须服务器确认。近战技能用数据化攻击体时间轴，服务器在关键帧或固定步长做 Sweep/Overlap。需要延迟补偿时会限制回溯窗口，避免为了主控体验破坏公平性。

### Q10：动画性能预算怎么做？

**考点**：是否能建立分层预算，而不是只讲某个优化点。

**回答要点**：

- 先拆 Update、Evaluate、Post Process、物理、布料、Notify 等成本。
- 按重要度分层：主控角色、近处敌人、战斗相关目标、远处角色、不可见角色。
- 结合 URO、Significance、Animation Budget Allocator、骨骼 LOD、后处理降级。
- 关注峰值和低端机，不只看平均帧。

**原理补充**：

Significance Manager 本身不直接优化性能，它提供项目自定义的重要度评估框架；Animation Budget Allocator 则可以按固定 CPU 预算动态限制骨骼网格体动画 Tick。

**可用回答**：

> 我会先用 Insights 拆清楚动画成本在 Update 还是 Evaluate。Update 侧看状态机、变量计算、Montage、Notify 和主线程依赖；Evaluate 侧看骨骼数量、Blend 树、后处理和物理解算。之后按角色重要度做预算，主控和近战关键目标高质量，远处和不可见角色降频、插值或关闭非关键后处理。验证时看低端机峰值，而不是只看平均值。

### Q11：动画蓝图 Update 和 Evaluate 有什么区别？

**考点**：是否知道动画性能的基本拆分。

**回答要点**：

- Update：更新状态机、变量、Montage、Blend 参数、Notify 相关逻辑。
- Evaluate：根据当前动画图计算最终姿态，执行混合、骨骼评估、后处理等。
- Update 常影响 Game Thread 和动画逻辑依赖；Evaluate 常受骨骼数、混合复杂度和后处理影响。
- 优化要先定位瓶颈阶段。

**可用回答**：

> 我会先把动画性能拆成 Update 和 Evaluate。Update 更像“决定播什么、参数是什么”，Evaluate 更像“算出最终姿态”。如果卡在 Update，要查状态机逻辑、主线程变量访问和 Notify；如果卡在 Evaluate，要查骨骼数、Blend 树、Layer、Post Process 和物理。两个阶段的优化手段不同，不能混在一起讲。

### Q12：复杂姿态切换，比如趴姿 360 度起身怎么做？

**考点**：是否能处理姿态、方向、胶囊体和碰撞空间。

**回答要点**：

- 输入方向、角色朝向、相机朝向和目标起身方向要统一。
- 起身点需要做碰撞预检查，避免起身穿模或顶到障碍。
- 动画可按方向分段或用 Blend Space / Pose Matching 选取。
- 胶囊体尺寸变化要和动画阶段同步。
- 联机时服务器校验最终站立位置是否合法。

**可用回答**：

> 我会先把这个问题拆成方向选择、空间合法性和动画衔接。方向上根据输入和相机决定起身朝向；空间上提前 Sweep 检查胶囊体能否从趴姿切到站姿；动画上可以按方向分段或用 Pose Search 选择更近的过渡。胶囊体高度变化要绑定到动画阶段，服务器最终校验站立位置是否合法。

### Q13：小怪避让、击飞穿模、角色挤压怎么处理？

**考点**：是否能区分玩法碰撞和表现碰撞。

**回答要点**：

- 玩法碰撞：影响阻挡、命中、站位，必须稳定。
- 表现碰撞：影响视觉穿插、局部避让，可近似和降级。
- 群体避让用优先级、半径、速度障碍、局部 Steering 或简单排斥。
- 击飞要限制轨迹合法性，必要时做落点修正。
- Boss / 大怪周围可用导航禁区或动态阻挡代理。

**可用回答**：

> 我会先区分这是玩法问题还是表现问题。如果会影响命中、阻挡和站位，就要服务器权威或至少服务器可校验；如果只是视觉穿插，可以用本地避让、动画偏移或 IK 近似。击飞类动作要提前检查轨迹和落点，遇到墙体或大怪身体时按规则截断、滑移或转入受阻动作，不能简单让动画播完。

### Q14：多线程客户端框架怎么设计？ECS 在里面起什么作用？

**考点**：是否知道多线程不是“把 Tick 丢出去”，而是要先解决数据组织、依赖调度、线程安全和结果同步。ECS 是这个问题里的高频追问点。

**回答要点**：

- 先梳理依赖图和更新顺序。
- ECS 的价值不是“天然多线程”，而是把对象拆成 Entity、Component、System，让数据更连续、依赖更清晰、批处理更容易并行。
- System 调度要基于读写依赖：只读系统可以并行，写同一组件的数据必须串行、分阶段或用命令缓冲合并。
- 适合 ECS 的模块：大批量、规则一致、对象间耦合弱的逻辑，如小怪群体、AI 感知、Buff Tick、投射物、寻路请求、远距离表现更新。
- 不适合强行 ECS 化的模块：强手感链路、复杂动画状态、强 UObject/Actor 生命周期依赖、需要大量蓝图/美术编辑的表现逻辑。
- 输入、战斗判定、移动校验等强同帧链路要谨慎异步。
- 表现、远距离动画、AI 感知、非关键物理可错帧或异步。
- 用快照、双缓冲/三缓冲、Command Buffer 交换数据，避免工作线程直接读写 UObject 状态。
- 验证手感延迟和一致性风险。

**原理补充**：

传统 OOP/Actor 模型方便表达单个对象行为，但大量对象 Tick 时容易出现虚函数分发、缓存不连续、依赖隐式、并行困难等问题。ECS 把“身份、数据、逻辑”拆开：Entity 是 ID，Component 是纯数据，System 按组件集合批量处理。这样更容易做 SoA 数据布局、分块遍历、Job 调度和读写依赖分析。

但 ECS 不是银弹。动作游戏 3C 里，主控角色的输入、移动、相机、动画和战斗反馈通常需要强时序和强调试可见性，不一定适合完全 ECS 化。更现实的方案是混合架构：核心主控链路保留 Actor/组件表达，大规模群体和可批处理逻辑放进 ECS；两边通过快照和命令缓冲同步。

**可用回答**：

> 我会先把多线程问题拆成数据组织和任务调度。ECS 的价值在于把 Entity、Component、System 拆开，让大量同类对象的数据更连续，System 的读写依赖更清楚，适合批处理和并行调度。比如小怪群体、AI 感知、Buff Tick、投射物、远距离表现更新都适合 ECS 化。但主控角色的输入、移动、镜头、战斗判定这条链路要保证手感和同帧一致性，不会为了 ECS 而强行拆散。落地上我倾向混合架构：强交互链路保留 Actor/组件，批量逻辑进 ECS，线程之间用快照、双缓冲和 Command Buffer 交换结果，避免工作线程直接读写 UObject。

### Q15：反作弊和客户端信任边界怎么定？

**考点**：是否知道体验和安全之间的取舍。

**回答要点**：

- 必须服务器约束：位置合法性、关键技能触发、伤害、资源、CD、状态切换。
- 可适当信任客户端：局部表现、镜头、非关键动画、低风险探索移动。
- 校验分级：硬拒绝、软纠正、异常积分、日志回放。
- 校验频率要看风险和服务器成本。

**可用回答**：

> 我的原则是核心玩法状态必须服务器可约束，比如位置、伤害、CD、资源和控制效果。客户端可以负责表现和预测，但不能单方面决定高价值结果。对于滑翔、载具这类偏体验的移动，可以给主控端一定信任度，但要做速度、加速度、地形、碰撞和状态机合法性校验，并用异常积分处理边缘情况。

### Q16：日常工作中如何使用 AI，尤其是 SDD？

**考点**：是否能把 AI 从“写代码工具”提升为需求澄清、方案设计、验证闭环和团队工程流程的一部分。

**回答要点**：

- 我会把 SDD 理解为 Spec-Driven Development，也就是先写清规格，再让 AI 辅助拆解、实现和验证。
- 日常不会直接让 AI “上来写代码”，而是先明确需求、约束、验收标准、边界 case 和验证方式。
- AI 适合做方案调研、需求拆解、测试用例生成、工具脚本、日志分析、性能数据整理、文档沉淀和代码草稿。
- 对游戏客户端尤其要强调验证：编译、自动化测试、真机/低端机验证、Unreal Insights 性能数据、Code Review。
- 不能把敏感代码、内部数据、未公开资源和账号密钥直接交给外部 AI；团队要有上下文管理和安全边界。

**SDD 工作流**：

1. Spec：先写清目标、非目标、输入输出、时序、网络权威、性能预算和验收标准。
2. Design：让 AI 辅助列方案和风险，但最终由人做架构取舍。
3. Tests：让 AI 根据规格补测试点、弱网场景、边界 case 和回归清单。
4. Implementation：让 AI 按小任务生成草稿，人负责接入项目架构和处理关键逻辑。
5. Verification：用编译、测试、性能采样和实际体验验证，不用“看起来对”替代验证。
6. Review：把 AI 产物当初稿审查，重点看隐含假设、线程安全、网络一致性、性能和可维护性。

**可用回答**：

> 我日常使用 AI 不会从“帮我写代码”开始，而是从 SDD 开始。也就是先把规格写清楚：这个功能解决什么问题，哪些不做，输入输出是什么，网络权威在哪里，性能预算是多少，怎么验收。然后让 AI 辅助拆方案、列风险、补测试用例、写工具脚本或生成代码草稿。对游戏客户端来说，AI 不能替代手感判断、架构取舍和性能验证，所有结果都要回到编译、测试、真机体验、Unreal Insights 数据和 Code Review。这样 AI 才是工程流程的一部分，而不是不可控的代码生成器。

## 4. 必须掌握的知识点和原理

### 4.1 网络同步四概念

- 延迟：网络传输耗时，发包频率不能消除。
- 采样间隔：状态更新离散程度，提高发包频率可以降低。
- 平滑性：模拟端视觉连续程度，靠插值/外插/平滑修正改善。
- 权威一致性：客户端和服务器最终是否一致，靠服务器校验与纠正保证。

面试中如果被指出“提高发包频率不能减少延迟”，要立刻校准：

> 是的，这里要区分 RTT 和采样间隔。发包频率改善的是轨迹采样连续性，不降低网络延迟。延迟本身要靠预测、补偿和规则约束处理。

### 4.2 动画优化基本路径

1. 用 Unreal Insights / Stat 拆成本。
2. 判断瓶颈在 Game Thread、Worker Thread 还是 Render Thread。
3. 拆 Update / Evaluate / Post Process / Physics / Cloth。
4. 优先处理峰值卡顿，再处理平均成本。
5. 用 URO、Significance、Animation Budget、骨骼 LOD 做分级预算。
6. 每个优化都要说明代价：画质下降、调参成本、边界 case、维护复杂度。

### 4.3 Motion Matching 的调试重点

- 数据库是否覆盖目标动作空间。
- Feature 是否和玩法目标一致。
- 权重是否导致脚滑、抖动或动作二义性。
- 是否需要按状态切库，避免搜索空间过大。
- 是否和 Motion Warping、Distance Matching、Stride Warping 组合。
- 是否保留战斗技能时间轴的确定性。

### 4.4 大怪 / Boss 判定设计原则

- 表现骨骼可以复杂，玩法代理必须简化。
- 判定数据要可复现、可校验、可降级。
- 关键攻击用时间轴驱动，不依赖客户端表现动画。
- 部位越多越真实，但服务器成本和调试复杂度越高。
- PVP 比 PVE 更偏服务器权威；PVE 可以根据体验适当宽松。

### 4.5 回答优化问题的三件套

每个优化案例都按这个结构准备：

1. 瓶颈：具体卡在哪里，如何定位。
2. 方案：做了什么，为什么这样做。
3. 结果：收益量级、代价、适用边界。

示例：

> 瓶颈在 Evaluate 阶段，主要受骨骼数量和后处理链路影响。方案是对非关键骨骼和后处理做分级裁剪，并配合角色重要度降级。收益是单角色动画评估成本有明显下降，代价是需要梳理资源依赖，避免某些挂点、IK 或后处理引用缺失。

### 4.6 ECS 与多线程客户端框架

ECS 面试里不要只背“Entity、Component、System”三个词，要讲清它为什么能支撑多线程：

- 数据连续：同类 Component 可以按块存储，缓存命中率更高，适合 SIMD 和批处理。
- 依赖显式：System 声明读写哪些 Component，调度器才能判断哪些任务能并行。
- 生命周期清晰：Entity 只是 ID，数据和逻辑解耦，批量创建、销毁、迁移更容易。
- 结果合并可控：跨线程修改结构时用 Command Buffer 延迟提交，避免遍历时改集合。
- 和 UE 对接要谨慎：UObject/Actor 通常不是线程安全对象，ECS 线程里应处理快照数据，最后回主线程提交表现或生命周期变化。

适合 ECS 的方向：

- 大量小怪或 NPC 的感知、简单决策、LOD 更新。
- Buff、状态、技能冷却、投射物、区域效果等批量规则。
- 远距离角色表现、非关键动画预算、可错帧更新逻辑。
- 服务器或 DS 上的大量实体模拟。

不适合硬塞 ECS 的方向：

- 主控角色输入、相机、移动手感和强战斗反馈。
- 复杂 Montage / AnimBP / 美术调试链路。
- 与 UObject 生命周期、蓝图事件、资源加载强耦合的逻辑。

可用结论：

> ECS 的核心价值是数据导向和可调度性，不是把所有业务都重写成组件。真正落地要看对象规模、耦合度、同帧要求和调试成本。动作游戏里我会优先把大批量、规则一致、可错帧的系统 ECS 化，把主控手感链路留在更直观、更可控的架构里。

## 5. 建议准备的 3 个 STAR 案例

### 案例 A：动画初始化或首次更新卡顿

- Situation：多人同屏或复杂角色首次出现时，动画初始化造成尖峰。
- Task：降低主线程卡顿，不影响角色进入场景的表现正确性。
- Action：拆初始化逻辑、延后非关键计算、复查 URO / 首帧更新策略、用 Insights 定位。
- Result：尖峰降低到可接受范围，低端机表现更稳定。

### 案例 B：骨骼裁剪 / 动画 Evaluate 优化

- Situation：复杂角色骨骼和后处理链路导致动画线程成本高。
- Task：在不明显损伤表现的前提下降低单角色 Evaluate 成本。
- Action：区分核心骨骼和非核心骨骼，配合骨骼 LOD、后处理降级和重要度分层。
- Result：单角色动画评估成本获得二到三成量级改善，代价是资源依赖需要治理。

### 案例 C：弱网移动同步与校验

- Situation：特殊移动在弱网下出现拉扯、误判或服务器纠正频繁。
- Task：保持主控手感，同时避免服务器状态失控。
- Action：区分固定轨迹和自由输入，固定轨迹参数化复现，自由输入预测 + 校验 + 平滑纠正。
- Result：百毫秒级延迟和少量丢包下体验可接受，同时保留异常检测。

## 6. 面试前一页速记

**核心卖点**：

- 有 UE 动作 3C、动画系统、联机移动和性能优化经验。
- 能从控制权、时间轴、权威数据、动画表现和性能预算拆问题。
- 能把 Motion Matching、CMC/Mover、Motion Warping、动画预算、服务器判定代理放在同一套方案里讲。

**最容易被追问的坑**：

- 不要说“提高发包频率减少延迟”，要说“减少采样间隔，改善连续性”。
- 不要说“服务器跑完整骨骼”，要说“服务器维护简化玩法代理”。
- 不要说“Motion Matching 解决所有动画”，要说“适合连续移动，不适合完全接管强确定战斗技能”。
- 不要只讲优化结果，要讲定位方法、收益量级、代价和边界。
- ECS 相关问题不要只背概念，要说清数据连续、依赖显式、System 调度、Command Buffer、与 UObject/Actor 的边界。
- AI 相关问题不要只说“提高效率”，要说 SDD：规格先行、AI 辅助、验证闭环、安全边界。
- 不清楚的实现不要硬编，给出验证路径。

**万能回答框架**：

> 这个问题我会先拆成三层：玩家手感、服务器权威、表现质量。主控端用预测保证输入响应，服务器用可复现数据保证规则正确，模拟端用插值/外插和平滑保证视觉连续。具体技术选型取决于动作是否固定轨迹、是否 PVP 高风险、是否需要强动画表现，以及低端机性能预算。
